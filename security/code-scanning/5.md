## What CodeQL reported

The transcript endpoint takes the attempt number from the request path, parses it with
[`strconv.Atoi`](https://github.com/bitwise-media-group/patchy/blob/d8f4c1ca5a716ad2fb95dfcd1e90c9e64553e030/internal/web/transcript.go#L63),
and converts the result to `int32` at
[line 69](https://github.com/bitwise-media-group/patchy/blob/d8f4c1ca5a716ad2fb95dfcd1e90c9e64553e030/internal/web/transcript.go#L69)
with only a lower-bound check in between:

```go
    attempt, err := strconv.Atoi(r.PathValue("attempt"))
    if err != nil || attempt < 1 {
        http.Error(w, "invalid attempt", http.StatusBadRequest)
        return
    }

    run, err := s.findRun(r.Context(), finding, kind, int32(attempt))
```

`Atoi` returns an `int`, which is 64-bit on every platform the status server ships on, so the `attempt < 1` guard admits
any positive value up to `math.MaxInt64` and the narrowing conversion then wraps it modulo 2³².

## Remediation

True positive on the conversion, with no security impact. The rule's premise holds exactly as stated — the value is
attacker-controlled, parsed at 64 bits, and narrowed to 32 with no upper bound — and the wrap is reachable rather than
theoretical:

1. **The truncation is real and silent.** `4294967297` (2³² + 1) passes the `< 1` guard as a 64-bit `int`, then narrows
   to `1`. A request for `/api/findings/finding-aa-1/runs/investigation/4294967297/transcript` is answered `200 OK` with
   **attempt 1's** conversation rather than rejected. `4294967296` narrows to `0` and `2147483648` narrows to
   `-2147483648`; both then miss and return `404`.
2. **It cannot cross an authorization boundary.** The handler calls
   [`s.authorize`](https://github.com/bitwise-media-group/patchy/blob/d8f4c1ca5a716ad2fb95dfcd1e90c9e64553e030/internal/web/transcript.go#L58)
   before parsing anything, and that check is
   [namespace-wide](https://github.com/bitwise-media-group/patchy/blob/d8f4c1ca5a716ad2fb95dfcd1e90c9e64553e030/internal/web/server.go#L130-L153)
   — it resolves a single "may view findings in this namespace" grant, not a per-finding one. Any caller who can reach
   the truncated attempt is already entitled to read every transcript it could reach.
3. **It cannot cross a finding boundary either.** The narrowed value is only ever interpolated into the run's own object
   name
   ([investigation](https://github.com/bitwise-media-group/patchy/blob/d8f4c1ca5a716ad2fb95dfcd1e90c9e64553e030/internal/web/transcript.go#L115),
   [remediation](https://github.com/bitwise-media-group/patchy/blob/d8f4c1ca5a716ad2fb95dfcd1e90c9e64553e030/internal/web/transcript.go#L123)),
   and the run that comes back is re-checked against its own `findingRef` at
   [line 132](https://github.com/bitwise-media-group/patchy/blob/d8f4c1ca5a716ad2fb95dfcd1e90c9e64553e030/internal/web/transcript.go#L132)
   before any content is streamed. It indexes runs _within_ the finding already named in the path; it cannot select a
   different finding's run.
4. **Nothing else is derived from it.** The value is not a length, capacity, index, or allocation size, so the CWE-190
   consequences the `high` security-severity anticipates do not arise here. The rating overstates this instance.

So the defect is a correctness one — a nonsense attempt number yields a confidently wrong `200` instead of a `400` —
rather than a disclosure. It is still worth fixing: the endpoint is the one place a caller picks which run to read, and
silently answering about a different run than the one requested is exactly the kind of quiet mismatch that makes a
transcript view untrustworthy.

The fix is the rule's own recommended form — parse at the width the value is used at, so the range check is the parse:

```go
    attempt, err := strconv.ParseInt(r.PathValue("attempt"), 10, 32)
    if err != nil || attempt < 1 {
        http.Error(w, "invalid attempt", http.StatusBadRequest)
        return
    }
```

`ParseInt` with `bitSize` 32 returns `strconv.ErrRange` for anything outside `int32`, so the existing error branch now
rejects the out-of-range values it previously admitted, and the subsequent `int32(attempt)` is provably in range.
`TestTranscriptRejectsOutOfRangeAttempt` covers the wrap values alongside the ordinary rejections; against the unfixed
handler its `4294967297` case fails with `status = 200, want 400`, which is the defect stated as a test.

## Resolution

Recommended for remediation, and fixed on the PR [#96](https://github.com/bitwise-media-group/patchy/pull/96) branch
(`feat/agent-log`) where CodeQL raised it. The outcome moves to **Remediated** with the commit link once that lands, and
the alert closes when CodeQL re-analyzes.
